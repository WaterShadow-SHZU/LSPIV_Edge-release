# LSPIV_Edge 多核性能分析

> **说明**：本文是开发过程中的分析与评估记录，保留了当时的原始数据与推理过程，
> 因此提到的路径可能仍是开发期的目录名（`velocimetry_solver-master/sources` 即
> 当前仓库的 `tools/solver-patches/`）。**结论部分仍然有效**；要查最新用法请看
> [ARM 部署说明](ARM-DEPLOYMENT-zh.md) 与 [性能说明](PERFORMANCE.md)。

结论先行：**"多开解算器"就是这台机器上最优的多核用法；把线程塞进单个解算器进程，对整批任务的吞吐几乎没有帮助。** 而真正吃掉时间的，一半是 `PIV.exe` 自己的固定开销（进程启动 + 读 PGM + 写结果），另一半原本是调度层"每对图像都删一遍文件"——后者已经砍掉，见第 2.1 节。

> 本文数字来自本机基准测试（1089×591 的 PGM，128 个网格点，935 帧）。测试机器是 4 大 + 4 中 + 4 小的大小核。**结论看比例，绝对值换台机器会变**；要让 `bench` 报出你自己机器上的数：
>
> ```bat
> py -3 lspiv_batch.py bench --calib <校准目录> --img-transf <img_transf 目录>
> ```

## 1. 为什么 GUI 只用单核

解算器早就带多核能力。`tools/solver-patches/makefile` 第 106 行：

```make
openmp = YES
```

Windows 和 Linux 目标都用这套 `FFLAGS`（含 `-Dopenmp -fopenmp`），所以 **随包发布的 `PIV.exe` / `PIV.x` 就是 OpenMP 版本**——在二进制里能直接搜到 `GOMP_parallel`、`libgomp`、`omp_get_num_threads` 等符号。

线程数从命令行第一个参数读（`sources/PIV.f90` 第 70–74 行）：

```fortran
ncore = 1                                   ! 顺序版的默认值
#ifdef openmp
   iarg = iarg+1 ; call get_command_argument(iarg,param3)
   read(param3,'(i2)') ncore                 ! 只认两位数字，最大 99
#endif
```

而 GUI 主程序 `fudaa-lspiv-master/src/main/java/org/fudaa/fudaa/piv/io/PivExeLauncher.java` 里，启动解算器的地方是：

| 位置 | 代码 | 结果 |
|---|---|---|
| 第 1214 行（PIV 逐对计算） | `FuLib.runProgram(new String[]{exePath+File.separator+EXE.PIV+EXE_EXT}, prjTmp);` | 无参数 → `ncore` 保持 1 |
| 第 1052 行（正射逐帧） | `FuLib.runProgram(new String[]{exePath + File.separator + EXE.transf_a + EXE_EXT}, prjTmp);` | 无参数 → `ncore` 保持 1 |

**GUI 一个参数都不传，所以 PIV 和正射都是单核**，并且第 1185 行是一个普通的 Java 串行循环，一对一对地算。这就是 GUI 慢的原因。

顺带说明：这**不是**"Java 串行导致的"。同一个文件里 Java 明明在用多线程（第 217 行 `KillProcessThread extends Thread`，第 409/523/1435 行用 `FuLib.runProgramAsync` 并发跑进程），是 PIV 这条路径被**写成**了串行循环。另外整个 Java 源码里没有任何核数/线程数设置项，所以在 GUI 里也调不到。

`LSPIV_Edge` 绕开了这个限制：不改解算器，直接并行开多个 `PIV.exe` 进程，每个算一对。这就是"多开解算器"。

## 2. 一对图像的耗时构成

受控实测（同一台机器、同一工作目录、同一对图像），只给 `PIV.exe` 子进程本身计时，每个线程数重复多次取最小值：

| 线程数 | `PIV.exe` 内部耗时 |
|---|---|
| 1 | 0.135 s |
| 2 | 0.125 s |
| 4 | 0.117 s |
| 12 | 0.115 s |

即**单对内部加速比 1.15–1.21×**，可并行部分约占 `PIV.exe` 的 14–19%（多次运行落在 16–19%）。

按 `t(T) = a + c/T` 拆开（`a` = 进程启动 + 图像 I/O + 写结果，`c` = 互相关核心）：

| 组成 | 耗时 | 占 `PIV.exe` | 多线程能加速吗 |
|---|---|---|---|
| 互相关核心 `c` | 0.020–0.026 s | ~16% | 能 |
| 进程启动 + 图像 I/O + 写结果 `a` | 0.110–0.115 s | ~84% | 不能 |

所以 `ncore=1 → 12` 只有约 **1.2×**。多线程只能碰到那 16%。

`a` 里的大头是**读 PGM**：`PIV.f90` 第 87–88 行把文件名写死成 `img_transf/image1_transf.pgm`、`image2_transf.pgm`，而 `sub_transf_23D.f90` 的 `read_PGM_P2_solver`（第 84–138 行）只认 ASCII 的 P2——它用 `read(lw,*)` 把 64 万个数字当文本解析一遍。一张 2.5 MB 的 P2（643 599 个像素）解析约 0.04 s，一对就是 0.08 s，占 `a` 的七成以上。**换 P5 二进制格式读图是这一层唯一的大杠杆，但必须重编译解算器**（见第 7 节）。

> 本机单对耗时抖动很大：同一配置的最小值与中位数能差 40%。上表一律用最小值，它代表"这一对没被打断"的情形，适合判断扩展性。

## 2.1 每对图像的 Python 侧开销：删除文件是元凶

改这一层之前，Python 调度层每对图像要付：3 次 `mkdir` + 4 次拷贝（`PIV_param.dat`、`grid.dat` 和两张 2.5 MB 的 PGM）+ 结果移出 + `rmtree` 掉整个工作目录。把这几步拆开单独计时（12 对，串行）：

| 步骤 | 耗时 |
|---|---|
| 3 次 `mkdir` + 4 次 `copy2`（含 5 MB 图像） | 0.005 s |
| `PIV.exe` | 0.139 s |
| 结果移出 + `rmtree` 工作目录 | **0.145 s** |
| 合计 | **0.29 s** |

维护工作目录的代价和跑解算器本身一样贵。再往下拆一层，把每个文件系统调用单独量：

| 操作 | 耗时 |
|---|---|
| 写一个 2.5 MB 文件 | 0.0008 s |
| 拷贝一个 2.4 MB PGM | 0.0016 s |
| `os.link` 两个文件 | 0.001 s |
| 移动（改名）结果文件 | 0.0004 s |
| **删除一个 2.5 MB 文件** | **0.103 s** |
| **删除一个装着 2 张 PGM + 1 个 dat 的目录** | **0.135 s** |

删除是唯一昂贵的一项，而且**和文件大小无关**：0 字节、1 KB、256 KB、2.5 MB 的文件删起来都是 0.117 s（各测 6 次）。固定延迟而不是 I/O 时间，说明是某个拦截层（杀毒软件实时防护 / 云同步 / 索引服务的文件系统过滤驱动）在每次删除时同步做检查。同一个测试放到 `%TEMP%` 下跑，删除只要 0.0004 s——**快 290 倍**，典型的路径策略而非磁盘问题。

一次 934 对的运行，旧写法要删 1868 张图像加 934 个目录树；新写法在进程退出前一次性删掉几个工作目录就够了。

代码已经改成：

- **每个工作进程一个常驻工作目录**（`tmp/worker_<pid>`），用 `copyfile` 原地覆盖两张图——覆盖是写，不是删；
- 结果用 `os.replace` 移出（改名，微秒级），顺带保证 `vel_raw/piv.dat` 不会留到下一对（PIV 用 `status='unknown'` 打开输出文件，旧文件更长时会残留尾巴）；
- 整批结束后才删一次 `tmp`；有失败则保留现场供排查。

实测 24 对：1/4/8/12 进程下都比旧写法快 **1.9–2.0×**；改完后"每对端到端"从 0.29 s 降到 **0.140 s**（其中 `PIV.exe` 0.135 s，Python 侧只剩 0.005 s）。

正确性验证：新旧两种写法各跑两遍同一对图像，`vel_raw/piv*.dat` 的第 1–5 列和第 9 列**逐位相同**。第 6–8 列本来就不可复现——同一份输入连跑两次的旧代码自己也对不上，这是第 5 节那个"未初始化内存"缺陷，与本次改动无关。

另外，视频路径里 `normalize_pgm`（把 `transf_a` 输出的 5 字符宽 P2 规范成单空格 P2）原来用纯 Python 逐字节分词，一张 2.5 MB 图要 **0.33 s**，934 帧就是 5 分钟。改成按行 `split()`/`join()` 的 C 级实现后是 **0.040 s（8.3×）**，输出逐字节相同（两种输入的 SHA-256 都比对过）。整条 `video` 流水线产出的 `img_transf/*.pgm` 与改动前**逐字节一致**。

> 这个开销换台机器可能小得多。`bench` 现在自己会跑这段测量（输出里的 `filesystem profile` 一节）并报出"删一次 = 写多少次"：写和删差不多贵时，复不复用工作目录都无所谓；差两个数量级时，复用就是白拿的 2 倍。

## 3. 为什么"给一对开多线程"救不了整批

设一对图像耗时 `a + c/T`：`a` 是启动与 I/O（跟线程数无关），`c` 是相关计算，`T` 是线程数。核数为 `B`，`N` 对图像。

- 全用进程：`W = B`、`T = 1`，总时间 ≈ `(N/B)(a + c)`
- 全用线程：`W = 1`、`T = B`，总时间 ≈ `N(a + c/B)`
- 一般情形：`W × T ≤ B`，总时间 ≈ `N(aT + c)/B`

**总时间对 `T` 单调递增，`T = 1` 时最小。** 多线程缩短的是"当前这一对"，缩短不了"这一批"。

上游作者在 `sources/solver_appli.f90` 的批处理 PIV（第 1425–1433 行）里就是这么做的，注释写得很明白：

> `routine de traitement PIV par lot`
> `la parallélisation concerne la boucle sur les paires d'images.`
> `la PIV proprement dite est trop courte pour que la parallélisation apporte vraiment quelque chose.`

也就是说：**上游自己的选择就是并行"图像对循环"，而不是并行"网格循环"**，并且批处理时显式给 `sub_PIV` 传 `ncore=1`（第 1481 行）。`LSPIV_Edge` 用多进程实现的是同一件事，方向没错。

`LSPIV_Edge` 的 `auto` 模式据此设计：**先用进程填满核，每进程 1 线程**；只有当图像对少到每个进程能分到至少 4 个核时，才把这些核开成原生线程——这样短任务不会白白空着核，而正常的整批任务又不会因为多开线程变慢。

这个 4 核门槛也是量出来的。6 对图像、12 核预算下：

| 计划 | 用时 |
|---|---|
| 6 进程 × 1 线程（`--mode process`） | 0.98 s |
| 6 进程 × 2 线程（改之前的 `auto`） | 1.18 s |

多开出去的线程省下的计算时间，补不回多进程抢盘、抢大核的代价。`--mode hybrid` 可以越过这个门槛，手动指定任意组合。

## 4. 批处理实测扩展性

48 对图像，`--mode process`（改完第 2.1 节之后的数字）：

| 并发进程数 | 用时 | 加速比 | 吞吐 |
|---|---|---|---|
| 1 | 7.33 s | 1.00× | 6.6 对/s |
| 2 | 3.74 s | 1.96× | 12.9 对/s |
| 4 | 2.14 s | 3.42× | 22.4 对/s |
| 6 | 1.67 s | 4.38× | 28.7 对/s |
| 8 | 1.45 s | 5.06× | 33.2 对/s |
| 12 | 1.36 s | 5.39× | 35.3 对/s |

（同一批任务在改之前是 8 进程 1.89 s、12 进程 1.92 s，只有 3.7×——旧的表把"删除开销"也算进了扩展性，所以看起来在 8 核就撞墙。移除删除之后曲线明显变好。）

8 与 12 之间只差 6%，落在测量噪声里，所以 `bench` 会把这种差距判为"平手"，继续推荐用满预算（12），而不是让你为了 6% 去牺牲 4 个核。

12 核换来 5.4× 而不是 12×，**主要是大小核架构的正常现象**（本机 4 大 + 4 中 + 4 小）：超出的核是小核，单个吞吐远低于大核。6→8→12 的边际收益（+0.68×、+0.33×）正好是这个形状。要选这台机器上的最佳并发数，用 `bench` 量一下 `--cpu-budget`。

## 5. 发现的两个解算器缺陷

都在 `sources/sub_PIV.f90`，影响 `vel_raw\piv*.dat` 的第 6、7、8 列（`sigma_n%`、`sigma_m%`、`aire`）。**流速列（第 1–5 列）是正确的**，且 `vel_transf.exe` 只读前 5 列，所以 `vel_real\` 与导出的 CSV 不受影响。

### 5.1 越界网格点写出未初始化的内存

`sigma_m`、`sigma_n`、`aire` 只在通过边界检查的分支里赋值（第 160、175 行），没通过的网格点直接把这几个数组的原始内存写进输出文件。

验证时，超出图像边界的网格点出现了不稳定值；重复运行后不稳定点与边界检查未通过的点一致。该问题与线程数无关，串行运行时同样出现。

### 5.2 累加量没有按网格点重置

`summ_c`、`esperance_m`、`esperance_n` 只在第 106 行（整个网格循环之前）初始化一次，之后一直累加下去，第 157–168 行拿它当"在当前搜索窗口内归一化的概率"用。所以**除第一个网格点外，所有点的标准差统计都是错的**。

这也是"传不同线程数会改变第 6、7 列"的真正原因：这几个量被 OpenMP 私有化后，每个线程带着未定义的初值和不同的累加历史，结果自然随线程数变化。**不是数据竞争，而是初值语义问题。**

要修必须重新编译解算器：把 `summ_c` 等移到循环内重置，并显式初始化 `sigma_m/sigma_n/aire`。修完输出才可复现。

## 6. 已经做完的改动

`lspiv_batch.py`：

**多核调度（上一轮）**

- 新增 `--mode auto|process|openmp|hybrid`、`--solver-threads N`、`--cpu-budget N`
- `auto`（默认）：按图像对数分配进程，每进程 1 线程；只有每进程能分到 ≥4 核时才开原生线程
- `openmp` 在没写 `--solver-threads` 时用满 `--cpu-budget`（否则它会退化成单进程单线程，比什么都不做还慢）
- 线程数自动限制在网格点数/图像行数以内，避免退出码 3
- 把 `--solver-threads` 透传给 `PIV.exe` 和 `transf_a.exe`（两者都认第一个参数为线程数）
- `bench` 重写为性能画像工具：单对线程标定 + 批处理进程数扫描 + 参数推荐
- `config.json` 支持 `solver_mode` / `solver_threads` / `cpu_budget`；读取时容忍 BOM

**调度层开销（本轮）**

- 常驻工作目录 + 原地覆盖，去掉每对的 `rmtree`/`mkdir`/重复拷校准文件（第 2.1 节）
- 结果改 `os.replace` 移出，顺便消除"旧 `piv.dat` 残留尾巴"的隐患
- `normalize_pgm` 增加按行的 C 级快速路径（0.33 s → 0.040 s，输出逐字节相同），非行对齐或 maxval≠255 时自动回退到通用实现
- `bench` 增加 `filesystem profile` 一节：实测本机的写/拷贝/链接/改名/删除耗时，并报出"删一次等于写多少次"

`bench` 的度量方式也一并修正过，值得记一笔：

- 每个工作进程额外上报 `PIV.exe` 子进程自己的耗时（`solver` 字段）。线程标定只用这个数，不再用包含建目录、拷文件、移结果的 `elapsed`——后者会被杀毒软件扫描拖出 100 ms 级的抖动。
- 线程标定样本提到"4 对 × 4 次"，取最小值。老的探针在同一台机器上先后给出 2.10× 和 1.10× 两个内部加速比，都是样本太少造成的；现在是稳定的 1.15–1.21×。
- 扫描结果里 8% 以内的差距判为平手（`BENCH_NOISE`），避免把噪声变成"建议你少用几个核"。

## 7. 还能做什么：需要 Fortran 编译器

本机没有 gfortran / make / cmake，所以下面这些都得先装工具链（选型和具体命令见 `OPTIMIZATION-ROADMAP-zh.md`）。

方向不是再加线程，而是**按上游 `solver_appli.f90` 的做法写一个批处理 PIV 主程序**：

1. 一个进程处理整批图像对（`!$omp parallel do` 在图像对循环上，每对 `sub_PIV(..., ncore=1)`）
2. `PIV_param.dat` / `grid.dat` 只读一次
3. 不再需要工作目录：主程序自己按 `dataset/iNNNN.pgm` 之类的路径读图，省掉 Python 侧剩下的 0.005 s/对，也省掉每对的目录切换
4. 换成二进制 P5 读图（新增一个 `read_PGM_P5`，替换 `read_PGM_P2` 的选择在 `sub_transf_23D.f90` 第 29 行那个过程指针上）——**这是最大的一项**：每对读两张 2.5 MB 的 P2 文本约 0.08 s，占 `PIV.exe` 的六成，P5 只要几毫秒
5. 顺手修掉第 5 节的两个缺陷，输出可复现

预期收益（按第 2 节的构成估算）：每对 0.140 s → 0.05–0.06 s，端到端再快 **2.5–3×**。加上 12 核并发，一张 935 帧的视频大约从原来的 1 分钟量级压到 20 秒量级。

代价：要维护一个 Fortran 分支，每次上游更新解算器都得重新对一次。如果只是自己用、跑得也不算频繁，现状可能已经够。
