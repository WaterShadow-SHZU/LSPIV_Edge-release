# 视频测流一键工具（LSPIV_Edge）

> 只要你会拖文件、会看 Excel，就能把一段测流视频变成一张流速表。

---

## 一、这个工具能干什么

一句话：**把它接到 Fudaa 后面，视频进去，流速表出来。**

原来的流程是：在 Fudaa 图形界面里一步步点——抽帧、正射校正、设参数、跑 PIV、导出。
本工具把这些步骤串成一条自动流水线：

```
一段视频  →  自动抽帧  →  自动正射校正  →  自动算流速  →  自动导出 CSV
```

**校准参数仍然必须先在 Fudaa 界面里做好一次**（正射范围、网格、PIV 参数）。
工具只负责"重复劳动自动化"，不负责"替你决定参数"。

---

## 二、开始之前，先准备两件事

### 第 1 件：解算程序（**已经帮你放好了**）

算流速要用的程序放在 `bin\windows\` 里，下载后可直接使用，不用自己编译：

- 解算程序：`PIV.exe`、`transf_a.exe`、`ortho_plan.exe`、`vel_transf.exe`、`filter.exe`、`vel_scal.exe`

运行前需另行安装 FFmpeg，并确保 `ffmpeg` 和 `ffprobe` 都能从 `PATH` 找到。Windows 和 Linux 的安装方式见 [FFmpeg 下载页](https://ffmpeg.org/download.html)。

ARM 板上的 `.exe` 不能运行，需在板上编译解算器，见
[ARM 部署说明](ARM-DEPLOYMENT-zh.md)。

> **这些程序是改过的版本，不是官方原版**。
> 相对官方 2024 版的主要改动：
> ① 读图支持 **P5 二进制**（一对图从约 14.8 秒降到约 0.25 秒），
>    算流速的 `PIV.exe` 和做正射的 `transf_a.exe` **都已改好**；
> ② 修了 `sub_PIV.f90` 两处缺陷，使结果**逐次可复现、且与线程数无关**。
> 前 5 列（真正用于算流速的列）与官方版**数值等价**（最大相对差 1.3e-15）。
>
> 想搞清楚到底改了什么，看 [源码改动说明](SOLVER-PATCHES.md)。
>
> **怎么确认自己拿到的是改过的版本**：`bin\windows\transf_a.exe` 的修改日期应该是 2026 年。
> 如果还是 2024 年的，说明只有一半改动到位，会在正射一步报 `exit=24`。

### 第 2 件：把校准文件放进 `calib\`

在 Fudaa 图形界面里完成一次完整的正射 + 网格 + PIV 参数设置，然后到该工程的
`outputs.dir` 目录里，把下面这些文件**复制**到本工具的 `calib\` 文件夹：

| 文件 | 作用（通俗说法） |
|---|---|
| `GRP.dat` | 地面控制点——告诉软件"画面上这个点，实际在哪" |
| `img_ref.dat` | 正射范围和分辨率——决定最后成果的尺度和边界 |
| `PIV_param.dat` | PIV 参数——算流速时的核心设置 |
| `grid.dat` | 计算网格——在哪些位置出流速值 |
| `h.dat` | 高程/水位输入 |
| `filters.dat` | 后处理滤波设置（**可选**，没有就跳过滤波） |

放齐这 5 个必需的（`filters.dat` 可选）就算准备好了。

> **注意**：这 6 个文件必须来自**同一次校准**。
> 相机挪了位置、测区变了，就要重新在界面里校准一次，并整套换新。

## 三、拿到视频怎么做（三步）

### 第 1 步：把视频拖到 `process_video.bat` 上

就这样，没有别的操作。

> 也可以双击 `process_video.bat`，然后按提示把视频路径粘进去再回车。

**支持常见的视频格式**（mp4、avi 等都行）。程序会自动完成：
抽帧 → 正射校正 → 算流速 → 写出结果。

### 第 2 步：等它跑完

窗口里会滚动输出进度。跑完会显示：

```
Done. See the new folder under runs.
```

然后按任意键关掉窗口。

跑的时间取决于视频长度和电脑性能。**第一次跑建议先用一小段短视频试**，
确认流程通了再说。

### 第 3 步：找到结果文件夹

每次运行都会在 **`runs\`** 下面新建一个文件夹，名字长这样：

```
runs\2026-09-14_1530_我的视频名\
```

时间戳 + 视频名，一看就知道是哪一次。里面装的就是这次的全部成果（见第五节）。

## 四、做完之后怎么检验（重点）

拿到结果**不能直接信**，一定要过一遍下面 4 道关。哪怕不懂算法，这 4 条也都能肉眼判断。

### 第 1 关：查文件齐不齐

打开 `runs\` 里你那次运行的文件夹，看这几个子文件夹：

| 文件夹 | 应该有什么 | 怎么判断正常 |
|---|---|---|
| `frames` | 从视频抽出来的图片 | 数量大致等于"视频秒数 × 帧率"。**0 张就是抽帧失败** |
| `img_transf` | 正射校正后的图片（灰色 .pgm） | 数量比 `frames` 少一点（首帧要做参考，属正常）。**打开一张看看：河道是不是被摆正了、有没有明显拉伸变形** |
| `vel_raw` | 单张的流速结果 `.dat` | 数量应该和 `img_transf` 对得上 |
| `vel_real` | 换算成实际坐标的流速 | **这是最终要用的东西**，必须有 |
| `export` | 导出好的 CSV 表格 | 运行 `export_csv.bat` 之后才会出现 |

任何一个是空的，先别急着看数，回去查原因（见第七节）。

### 第 2 关：把 CSV 导出来，看数

双击 **`export_csv.bat`**。它会自动处理**最新一次**运行，生成：

```
runs\<那次运行>\export\vel_real.csv   ← 实际坐标流速（最终成果）
runs\<那次运行>\export\vel_raw.csv    ← 图像坐标原始流速（中间结果）
```

用 Excel 打开 `vel_real.csv`（双击就能开）。表格列的含义：

| 列名 | 含义 |
|---|---|
| `file` | 这个数据点来自哪张图（对应第几对帧） |
| `i_or_x` | 位置坐标（第几列 / 多少米） |
| `j_or_y` | 位置坐标（第几行 / 多少米） |
| `vx` | 水平方向流速 |
| `vy` | 垂直方向流速 |
| `corr_or_status` | 相关系数或状态——**数值越高越可信** |

> 想指定某一次运行，把那个文件夹拖到 `export_csv.bat` 上即可。

### 第 3 关：看数值合不合理（三查）

把 `vx`、`vy` 两列选中，看 Excel 右下角的状态栏：

**① 有没有离谱的大值？**
`vx`/`vy` 的绝对值应该和你**目测的水流速度**在一个量级。
如果出现几十甚至上百（比如量级是"米/秒"却跳出 50），说明这一格算错了，
通常是对比度不够或者水面太反光。

**② 有没有成片一样的值？**
如果绝大多数格子数值完全相同，或者大批是 0，说明互相关没算出来
（水面太均匀、没纹理——玻璃一样平静的水面 LSPIV 是算不了的）。

**③ 方向对不对？**
`vx`、`vy` 的正负号表示流向。取几个点看看，**方向应该和你看水流的方向一致**，
不能有整片反过来的情况。

> **一句话原则**：水流是连续变化的。相邻格子的流速应该平滑过渡，
> **不应该出现"孤零零一个特别大的数"或者"棋盘格一样忽大忽小"**。
> 出现这种情况，就要考虑加滤波、或者换一段纹理更好的视频。

### 第 4 关：和已知数据对一下（最硬的检验）

如果你的测次有**流速仪实测值**（比如岸边放了个流速计、或者以前同水位测过），
把 CSV 里对应位置的流速拿来比一比。
量级一致、趋势一致，就可以放心用了。

### 附：想要一张流速箭头图

如果你电脑上装了 matplotlib，可以生成一张矢量预览图：

```text
py -3 preview_results.py
```

它会在运行目录下生成 `preview.png`，箭头方向就是流向。
**没装也没关系**，看 CSV 完全够用。

|---|---|

## 六、关于 P2 和 P5（解释一下，不影响你操作）

前面我提到的"P2 输入 / P5 输入"，说的是**图片的存法**，你不用管它，因为它已经自动处理好了。
但既然问了，用大白话解释一下：

`.pgm` 是这类软件常用的一种灰度图片格式，它有两种存法：

| 说法 | 大白话 |
|---|---|
| **P2** | **"文字版"图片**——每个像素的灰度值都写成一串数字，用空格隔开。一张 1089×591 的图要写 64 万个数字，文件 2.5 MB，程序还得把这 64 万个数字一个个从文字里读出来 |
| **P5** | **"压缩版"图片**——同样的像素，直接按二进制存，机器一读就是一片数据。文件只有 0.64 MB，读起来快得多 |

**里面装的像素是一模一样的**，只是"记账方式"不同。
所以我把它从 P2 换成了 P5，实测：

| 存法 | 每对图像算流速要多久 |
|---|---|
| P2（老） | 约 **14.85 秒** |
| **P5（现在默认）** | 约 **0.25 秒** |

**快了大约 59 倍**，而且文件还只有原来的 1/4 大。

> **说清一个前提**：这套 "P5 加速" 要能跑通，**读图的那几个程序都得认识 P5**。
> 算流速的 `PIV.exe` 和做正射的 `transf_a.exe` 分别有两个独立的读图函数，
> 两个都已改好，且都验证过 **P2 与 P5 输入产出逐字节相同的输出**。
> 如果你只换了其中一个，就会看到类似
> `transf_a.exe exit=24; output missing/empty` 的报错——那种情况下把
> `bin\windows\transf_a.exe` 一起换成新版即可。

### 那我需要注意什么？

**基本什么都不用注意**——工具已经默认用 P5，你拿视频拖上去就行，感觉就是"快了很多"。

只有一种情况要留心：
**如果你把 `bin\windows\` 里的解算器换回了官方原版**，
那个原版**不认识 P5**，必须告诉工具退回老格式：

- 在 `config.json` 里把 `"pgm_binary"` 改成 `false`，或
- 命令行加参数 `--no-pgm-binary`

否则会报错或结果全错。

### 第二个问题：现在必须用 Python 脚本吗？

**不需要。** 用法和你以前**完全一样**：

- 拖视频到 `process_video.bat` —— 照旧，推荐
- 双击 `export_csv.bat` —— 双击就行
- Python 只是**工具内部自己在用**，不是要你用

上面出现的 `py -3 lspiv_batch.py ...` 这些命令，是给"想多调一点参数"的人准备的高级入口。
**你完全可以一辈子不碰它们。**

## 七、常见问题

**Q：窗口一闪就没了 / 提示找不到程序？**
确认 `bin\windows\` 里有解算器 `.exe`，并且 `ffmpeg`、`ffprobe` 已安装且在 `PATH` 中。

**Q：提示缺少校准文件？**
检查 `calib\` 里 `GRP.dat`、`img_ref.dat`、`PIV_param.dat`、`grid.dat`、`h.dat`
是否齐全，而且来自**同一次**校准。

**Q：跑失败了怎么查？**
去 `runs\<那次运行>\tmp\` 里看输出信息。
失败时这个文件夹**不会**被删掉，就是留着给你排错的。

**Q：出现 `[FAIL] transform 0001 ... transf_a.exe exit=24; output missing/empty`
然后提示 `fewer than two transformed frames are available for PIV`？**
（已修复。如果你用的是更早的版本，请按下面的办法更新。）

这是**正射这一步**（把斜拍的画面摆正）失败了，不是抽帧或算流速的问题。
当时 `transf_a.exe` 只会读老式的"文字版"图片（P2），而工具现在默认写"压缩版"（P5），
两边对不上，于是每一帧都在第 1 步就停住，935 帧全失败。

修复办法：用本仓库的 `bin\windows\transf_a.exe` 覆盖原文件。
新版的判断依据是**读文件开头**，看到 `P5` 就按二进制读、看到 `P2` 就按文字读，
两种格式都能吃，不会误判。验证结果：同一张图分别用 P2 和 P5 输入，
正射输出**逐字节完全相同**。

**Q：CSV 里全是 0 或者乱七八糟？**
先分辨是"全 0"还是"部分 0"：

- **部分为 0**（正常）：网格边缘的点落在正射范围之外，本来就算不出来，
  解算器会把它标成 `-99`（相关系数那一列）。有效点比例取决于校准网格、
  正射范围和画面内容，应结合现场情况判断。
- **整列/整片全是 0**：多半是**水面太均匀没纹理**（平静水面、逆光反光）。
  LSPIV 靠追踪水面上的花纹/波纹，一点纹理都没有就没法算。
  建议换一段有波纹、有絮状物的视频。

**Q：相机换了 / 测区变了怎么办？**
必须回 Fudaa 界面**重新校准一次**，整套 6 个校准文件全部换新。
**千万不要**混用不同测次的控制点。

**Q：视频很长，能只算一部分吗？**
可以。命令行加 `--every N` 表示每隔 N 帧抽一帧（比如 `--every 5` 抽帧量降到 1/5）。
这属于进阶用法，用不到就忽略。

**Q：中间有一段"只有一个核在忙"，是卡住了吗？**
不是。那一段是在把抽出来的图片转成解算器能读的格式，
由 **8 个进程并行**完成，935 帧约 16.4 秒。
如果看到长时间单核忙，看第八节的时间表——花时间最多的是**正射校正**，
不是转图。**这不是卡住**，`frames` 文件夹里的图片数量在增加就说明在正常推进。

## 八、想了解更多（进阶，可选看）

下面这些是给"想搞明白原理、想把速度再压一压"的人看的。
**处理日常测流任务，看完第三节和第四节就够了。**

- **多核怎么用** —— 工具默认按图像对数开多个解算器进程并行跑。
  给单对图像开多线程其实帮助不大（解算器大部分时间花在启动和读写图片上，
  真正算互相关只占约 16%），所以默认每个进程只开 1 个线程。
  想自己调，用 `--workers`（并发进程数）和 `--cpu-budget`（总共用几个核）。

- **抽帧之后的转图一步是怎么并行的？**——

  那一段是"把抽出来的图片（PNG）转成解算器能读的图片（PGM）"。
  **每张图单独起一次 ffmpeg** 要付 935 次进程启动（935 帧，全挤在一个核上）；
  **整批一个 ffmpeg** 不再反复启动进程，但只有一个进程在解码，仍是一个核忙、其余闲着。

  采用的做法：把整份帧列表**切成 8 段，8 个 ffmpeg 同时解码**，并且让 ffmpeg
  **直接写出 P5 文件**，Python 连像素都不再搬。实测 935 帧：

  | 做法 | 这一步耗时 |
  |---|---|
  | 每帧一个 ffmpeg | 约 **172 秒** |
  | 整批一个 ffmpeg | 约 **78 秒** |
  | **8 个 ffmpeg 并行（当前做法）** | 约 **16.4 秒** |

  输出与老路径**逐字节相同**（三层回退路径各验证过一遍）。

  **这一步用几个进程是自动定的（最多 8 个），不受 `config.json` 里 `workers` 影响**——
  `workers` 只管后面"做正射 / 算流速"那一段。这样设计是因为这一步跑的时候
  后面还没开始，可以放心吃满核；而正射那一段你调过多少进程，实测 **4 个就到顶**
  （见下面"想知道这台电脑该开多少进程"）。

- **一次真实的 935 帧运行，时间花在哪**（12 核机器，实测两次）——

  | 阶段 | 耗时 | 占比 |
  |---|---|---|
  | 抽帧（视频 → PNG） | 约 30 秒 | — |
  | 转图（PNG → PGM） | **16.2 ~ 16.4 秒** | ~16% |
  | 正射校正（transf_a） | **39 ~ 50 秒** | ~46% |
  | 算流速（PIV） | 17.7 ~ 18.1 秒 | ~18% |
  | 换算实际坐标（vel_real） | 11 ~ 16 秒 | ~15% |
  | **合计（不含抽帧）** | **84 ~ 99 秒** | |
  | **端到端（含抽帧）** | **约 110 ~ 130 秒** | |

  正射那一段实测并行效率 **3.96×**（4 进程基本跑满），已经是这台机器的上限；
  再往上加进程反而更慢。**目前最大的头是正射，不是转图了。**

  这三次改动累计的效果：**转图这一段从约 172 秒降到约 16 秒**，
  端到端从约 5 分钟 → 约 3 分钟 → **约 2 分钟**。

- **想知道这台电脑该开多少进程** —— 跑一次摸底测试：

  ```text
  py -3 lspiv_batch.py bench --calib .\calib --img-transf .\runs\<某次运行>\img_transf --pairs 1:24 --sweep 1,4,8,12
  ```

  它会告诉你不同进程数下的耗时，并给一条推荐参数。

- **用历史数据重跑（不重新处理视频）** —— 直接对某次运行的 `img_transf` 跑 PIV：

  ```text
  py -3 lspiv_batch.py piv --exes .\bin\windows --calib .\runs\<某次运行>\resolved_calib --img-transf .\runs\<某次运行>\img_transf --out .\runs\_retest --pairs 1:8
  ```

  **关键**：`--calib` 要指向那次运行的 `resolved_calib\`，而不是 `calib\`——
  前者才是当次真正生效的参数。

  老数据里的 `img_transf\*.pgm` 是 P2 格式，想吃 P5 的加速要先转一遍：

  ```text
  py -3 ..\build\p2_to_p5_dir.py .\runs\<运行>\img_transf .\runs\<运行>\img_transf_p5 --workers 4
  ```

- **解算器（开源代码）的两个毛病，现在已经修好了** ——
  原版 `sub_PIV.f90` 里有两处初始化缺陷，会让 `vel_raw` 结果的第 6–8 列
  每次运行都不一样、还随线程数变。**前 5 列（真正算流速用的）不受影响**，
  所以 `vel_real` 和导出的 CSV 也没受影响。
  修好之后，同一输入连跑两次、或 1 线程 vs 4 线程，**9 列全部 0 差异**。
  详细分析见 [多核性能分析](MULTICORE-ANALYSIS-zh.md)。

- **ARM 设备（香橙派等）部署** —— 见 [ARM 部署说明](ARM-DEPLOYMENT-zh.md)。
  优化空间与可行性的原始评估见 [优化路线与评估](OPTIMIZATION-ROADMAP-zh.md)。
